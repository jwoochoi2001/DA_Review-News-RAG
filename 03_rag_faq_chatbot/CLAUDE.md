# 공통 작업 규칙

- 프로젝트 루트를 기준으로 상대경로를 사용한다.
- 원본 자료는 보존하고 가공 결과와 구분한다.
- 실제 파일명과 데이터 구조를 확인한 뒤 작업한다.
- 근거가 없는 사실을 만들지 않고 원문 출처를 유지한다.
- 개인 인증 정보와 API 키는 배포 파일에 포함하지 않는다.
- 요청한 작업까지만 수행한다.

## LLM Wiki 규칙 (wiki/)
Karpathy의 LLM Wiki 방식을 따른다. 세 층으로 나뉜다.
- **원본(data/)**: 소스 문서. LLM은 읽기만 하고 절대 고치지 않는다.
- **위키(wiki/)**: LLM이 만들고 관리하는 마크다운. 사람은 읽는다.
- **스키마(이 문서)**: 위키의 구조와 작업 절차.

### 구조와 이름
- `wiki/index.md`: 모든 페이지의 한 줄 요약 목록(내용 중심). 질문에 답하기 전에 가장 먼저 읽는다.
- `wiki/log.md`: 시간 순 작업 기록(추가만). 항목 형식은 `## [YYYY-MM-DD] ingest|query|lint|index|update | 제목`.
- 폴더: `products/`(제품), `entities/`(앱·조직), `topics/`(주제), `analysis/`(대조·공백 분석), `sources/`(원본 요약), `개요.md`.
- 파일 이름은 공백 대신 밑줄을 쓰고 이름이 겹치지 않게 한다. 링크는 `[[파일이름]]`(Obsidian 방식).
- 모든 페이지(index·log 제외)는 frontmatter에 `title`, `type`(product|entity|topic|source|analysis|overview), `sources`(인용한 원문 위치 목록), `updated`를 둔다.

### 출처 표기 (필수)
- 사실을 쓰는 모든 문장 끝에 `(출처: 제품_매뉴얼.md §3.2)`, `(출처: 제품_FAQ.csv #1)` 형식으로 근거를 적는다. §는 매뉴얼 절 번호, #는 FAQ 데이터 행 번호(머리글 제외)이다.
- 원문에 없는 내용은 쓰지 않는다. 숫자와 단위는 원문 표기를 그대로 쓴다. 원문에 없는 내용은 [[확인되지_않는_정보]]에 모은다.
- 두 원본이 어긋나면 한쪽을 고르지 않고 [[문서_간_일치_점검]]에 양쪽 출처와 함께 기록한다.

### 작업 절차
1. **ingest(새 원본 추가)**: 원본을 `data/`에 두고 → 읽어서 `sources/`에 요약 페이지 작성 → 관련 제품·개체·주제 페이지를 새로 만들거나 갱신(한 원본이 여러 페이지에 영향) → `index.md` 갱신 → `log.md`에 기록 → `python wiki_lint.py`.
2. **query(질문)**: `index.md`를 읽고 관련 페이지를 찾아 읽은 뒤 출처와 함께 답한다. 위키에 없으면 "확인할 수 없다"고 답한다. 가치 있는 답은 `analysis/`나 해당 주제 페이지에 반영하고 log에 기록한다.
3. **lint(점검)**: `python wiki_lint.py`(깨진 링크·고아 페이지·잘못된 출처·원문에 없는 숫자)를 돌리고, 모순·낡은 내용·빠진 주제는 직접 읽어서 점검한다. 결과를 log에 남긴다.
4. **챗봇 연결**: 위키를 고치거나 ingest한 뒤에는 `python ingest_wiki.py`로 위키 색인을 다시 만든다(원문 색인 `ingest.py`와 별개의 컬렉션). 챗봇(`app.py`, `rag_chain.py`)은 `KNOWLEDGE_SOURCE`(wiki 기본 / raw)로 위키와 원문 중 하나를 검색한다. 색인 대상은 products·entities·topics·개요이며 index·log·sources·analysis는 제외한다.
